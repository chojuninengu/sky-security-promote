Modern Cyber Defense Architecture

Robust defense requires two synchronized pillars: real-time analysis technology and a professional response team.

SIEM

(Security Information & Event Management)

The Central Technology Layer

A specialized platform that continuously aggregates, processes, and correlates event logs from across your entire infrastructure to immediately flag security incidents.

SOC

(Security Operations Center)

The Security Analyst Team

The specialized team of cybersecurity analysts who monitor the SIEM alerts 24/7, investigate suspicious activities, and coordinate incident response.

Differentiate between the tool (SIEM) and the people (SOC). A SIEM without a SOC results in unaddressed alerts; a SOC without a SIEM has no visibility.

Process 2: File Integrity Monitoring

Detecting unauthorized changes to critical system files

Goal: Show that Wazuh detects file changes in real time.

What Happens During This Simulation

The simulation quietly connects to the target machine and makes a series of small changes to a file in a sensitive system directory. First creating it, then editing it twice, then deleting it. These are exactly the kinds of actions that could indicate an attacker modifying configuration files or planting malicious scripts. Wazuh picks up each change instantly and logs it.

Show in Dashboard

Process 4: Brute-Force Detection

Simulate repeated failed SSH logins from a test machine

Prerequisites: Test endpoint with SSH enabled + separate test machine in the lab.

What Happens During This Simulation

The simulation mimics a common real-world attack where someone tries to break into a server by rapidly attempting many different passwords. It fires a series of login attempts against the target machine in quick succession. All of them intentionally wrong. Wazuh doesn't just log each failed attempt individually; it recognises the pattern and raises a single correlated alert flagging it as a brute-force attack in progress.

Show in Dashboard

  • Multiple failed authentication events
  • Source IP of the test machine
  • Target endpoint hostname
  • Correlated brute-force alert (e.g., rule ID 5763 if available)
"What you're seeing here is Wazuh recognising a pattern — not just one failed login, but many in a short window. That's the difference between someone mistyping their password and an attacker trying to force their way in. Wazuh knows the difference and alerts your team immediately."

Troubleshooting, Fallback & MITRE ATT&CK

Quick reference for common issues and the optional MITRE demo

Troubleshooting

No FIM alerts? Confirm path is monitored, repeat action, refresh dashboard.

Endpoint not in dashboard? Restart agent, verify connectivity, search by hostname.

Brute-force alerts unclear? Filter by hostname, source IP, or rule ID 5763.

Hydra missing? Install before session: sudo apt install hydra

YARA alert missing? Confirm the active response script is configured in ossec.conf and the Downloads directory is in the FIM monitored paths.

Fallback (Short on Time)

Download the eicar malware test file. Malware scan will automatically be triggerd. Use a pre-existing alert to show MITRE ATT&CK mapping without triggering a new simulation.

Optional: MITRE ATT&CK Mapping

  • Open any generated alert in the Wazuh dashboard
  • Navigate to the MITRE ATT&CK tab in alert details
  • Point out technique ID (e.g., T1110 — Brute Force) and tactic (e.g., Credential Access)
  • Filter alerts by ATT&CK technique across the entire estate

"Every Wazuh alert is automatically mapped to MITRE ATT&CK — helping teams understand not just what happened, but how the attacker operated."

Use the MITRE section for technical audiences only. The safest short demo is health check + FIM + one MITRE mapping from an existing alert. Troubleshoot quietly before the session starts.
